# infra

Pulumi program for Dollas deploy infrastructure. It is a pnpm workspace package (`@dollas/infra`) that the Vercel build never installs (Vercel installs `--filter @dollas/web...` only).

Today it does one thing (PEN-214): it creates the `dollas_app` **LOGIN** role in the Neon database and stores its connection string in Vercel as the sensitive variable `DATABASE_URL_APP`. The app connection pool logs in as that role, so Postgres row-level security binds the connection itself. The Neon owner URLs (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`) stay for migrations only.

PEN-211 (the full Vercel recipe) adds modules next to these:

```
infra/
  index.ts                         composes the stack
  Pulumi.yaml                      project "dollas", Node.js + TypeScript
  sql/dollas-app-login.sql         idempotent role SQL, run as the owner
  sql/verify-dollas-app.sql        what to check while logged in as dollas_app
  src/config.ts                    stack settings (namespace "dollas")
  src/database/app-login.ts        dynamic resource that runs the SQL and proves the login works
  src/database/app-login-sql.ts    SQL rendering, DATABASE_URL_APP building (unit tested)
  src/vercel/app-database-env.ts   DATABASE_URL_APP on the Vercel project
```

## Rules

- `dollas_app` is created only by `sql/dollas-app-login.sql`, run by Pulumi as the database owner. **Never** create or edit it in the Neon console, the Neon CLI, or the Neon API: those paths add the role to `neon_superuser`, which bypasses row-level security. The SQL refuses to continue (and changes nothing) if `dollas_app` is in `neon_superuser`, is a superuser, or has BYPASSRLS, REPLICATION, CREATEROLE, or CREATEDB.
- The app never creates the role or its password, at startup or at sign-in. On boot it only creates a `NOLOGIN` `dollas_app` if none exists (for the transition bridge) and re-applies table grants. It never changes LOGIN or the password.
- When `DATABASE_URL_APP` is set, the app refuses to start unless that login is `dollas_app` and is not a superuser, has no BYPASSRLS, CREATEROLE, or CREATEDB, is not in `neon_superuser` or any superuser or BYPASSRLS role, does not own the tables, and reaches the same database as `DATABASE_URL`.
- The password is 48 random letters and digits (about 285 bits), generated by `random.RandomPassword` and kept encrypted in Pulumi state. Neon requires at least 60 bits.

## One-time setup

You need the Pulumi CLI, pnpm, and two credentials. Neither credential goes in git or in shell history (`pulumi config set --secret` without a value prompts for it).

1. Install the Pulumi CLI (https://www.pulumi.com/docs/iac/download-install/), for example `curl -fsSL https://get.pulumi.com | sh`. Then run `pnpm install` from the repo root. Pulumi downloads its provider plugins (random 4.21.2 and pulumiverse vercel 5.4.1) on first use; there are no npm install scripts to allow.
2. Pick where state and secrets live: `pulumi login` (Pulumi Cloud, free for one person), or `pulumi login --local` with `export PULUMI_CONFIG_PASSPHRASE=...` kept in your password manager.
3. A Vercel token for the team that owns the `dollas` project: https://vercel.com/account/tokens.
4. The Neon **owner direct** URL (`neondb_owner`, host without `-pooler`). It is the value of `DATABASE_URL_UNPOOLED` on Vercel, also shown in the Neon console's connection details. Reading it there is fine. Do not create roles there.

```bash
cd infra
pulumi stack init production
pulumi config set dollas:vercelProjectId prj_BR3J6q8u5Mf2elb9J0Z5u4TQlrvN
pulumi config set dollas:vercelTeamId team_yhAulgIZyqJ2NaA2CU1yTZCn
pulumi config set --secret dollas:ownerDatabaseUrl   # paste the owner direct URL
pulumi config set --secret vercel:apiToken           # paste the Vercel token
```

Optional settings:

| Key | Default | Meaning |
| --- | --- | --- |
| `dollas:vercelTargets` | `production,preview` | Vercel environments that get `DATABASE_URL_APP`. Sensitive variables cannot target development. |
| `dollas:appDatabaseHost` | pooled form of the owner host (`ep-…-pooler…`) | Host in `DATABASE_URL_APP`. Serverless functions should use the pooler, like the integration's `DATABASE_URL`. |
| `dollas:appPasswordVersion` | `1` | Change it to rotate the password. |

`Pulumi.production.yaml` holds the encrypted settings and is git-ignored for now.

## Roll out (first time)

The order matters: the app has to stop forcing `NOLOGIN` before the login exists.

1. **Merge the PEN-214 PR** and let production deploy. Nothing changes yet: there is no `DATABASE_URL_APP`, so the app keeps the `SET LOCAL ROLE` bridge and logs a warning that the login is missing.
2. **Preview, then apply:**

   ```bash
   cd infra
   pulumi preview --diff
   pulumi up
   ```

   You should see 4 creates (the stack, the password, `dollas-app-login`, `database-url-app`). `dollas-app-login` runs the SQL as the owner and then logs in as `dollas_app` with the new password. If either step fails, `pulumi up` fails and the database is unchanged. The bridge keeps working throughout: it uses `SET ROLE`, which neither LOGIN nor the password affects.
3. **Check the login** (prints no secret):

   ```bash
   psql "$(pulumi stack output appDatabaseUrl --show-secrets)" -f sql/verify-dollas-app.sql
   ```

   Expect `current_user = dollas_app`, `f` for superuser, bypassrls, createrole, createdb, and neon_superuser, and `0` households visible (no member is set). A `permission denied for table household` instead means startup has not granted tables to `dollas_app` yet on this database; deploy once and check again.
4. **Redeploy production** so it picks up the new variable: in the Vercel dashboard, Deployments, the latest production deployment, **Redeploy**. Or with the CLI, `vercel redeploy <production deployment URL> --scope <team>`. Previews get it on their next build.
5. **Check the app.** The production function log at boot says `App pool connects as the dollas_app login (DATABASE_URL_APP).` and no longer warns about the bridge. Sign in and open Activity. As the owner, this should show app connections as `dollas_app`:

   ```sql
   select usename, application_name, count(*)
   from pg_stat_activity where datname = current_database()
   group by 1, 2 order by 1;
   ```

   The web app, Better Auth, and `/api/mcp` all share this pool.

## Rotate the password

```bash
cd infra
pulumi config set dollas:appPasswordVersion 2   # any new value
pulumi up
```

Then redeploy production right away (step 4 above). The old password stops working as soon as `pulumi up` finishes, and running deployments still hold it. Warm instances keep their open connection, but a cold start fails its login check until the redeploy is live. Rotate at a quiet time. A zero-downtime rotation would need a second login role; that is out of scope.

## Repair

- **Production refuses to start with "Could not log in with DATABASE_URL_APP … (28000)"** (`dollas_app` lost LOGIN) **or (28P01)** (password mismatch). Deployments built before PEN-214 ran `ALTER ROLE dollas_app NOLOGIN NOSUPERUSER NOBYPASSRLS` at boot on Vercel. On Postgres 16+ that statement fails for a non-superuser owner, so it most likely never took effect on Neon, but an old preview deployment could still try. Re-apply the SQL with the same password, then redeploy:

  ```bash
  pulumi up --replace 'urn:pulumi:production::dollas::pulumi-nodejs:dynamic:Resource::dollas-app-login'
  ```

- **Fall back to the bridge** (keeps row-level security, through `SET LOCAL ROLE`): delete `DATABASE_URL_APP` in Vercel, or run `pulumi destroy --target 'urn:pulumi:production::dollas::vercel:index/projectEnvironmentVariable:ProjectEnvironmentVariable::database-url-app'`, and redeploy.
- **`pulumi up` says dollas_app is in neon_superuser.** Someone created it in the Neon console. Delete that role in the Neon console, run `pulumi up --replace …dollas-app-login` (above) to create it cleanly, redeploy, and let startup re-apply the grants.
- `pulumi destroy` leaves the role in place on purpose. To retire it, run `ALTER ROLE dollas_app NOLOGIN` as the owner after the app no longer uses it.

## Preview deployments

As of 2026-10-10, previews and production share one Neon database. The Neon integration's `DATABASE_URL` and `DATABASE_URL_UNPOOLED` target both preview and production, with no per-branch values. So one `DATABASE_URL_APP` targets both too. If Neon preview branching is turned on later, each preview gets a branch `DATABASE_URL`, and a project-wide `DATABASE_URL_APP` would still reach production. The app refuses to start in that case (`DATABASE_URL_APP points at a different database than DATABASE_URL`). That would need per-branch `DATABASE_URL_APP` values and is a PEN-211 decision. Branches copy roles from their parent, including `dollas_app`.

## Follow-up: delete the bridge

Once production and preview both run with `DATABASE_URL_APP` (the boot log shows the login line, not the bridge warning), remove the PEN-213 bridge in one PR:

- `asAppRole`, `ASSUME_APP_ROLE_SQL`, and `assertAppRoleSubjectToRls` in `apps/web/src/db/app-role.ts` and `apply-migrations.ts`
- the `bridge` mode in `appPoolConfig` and `openAppDatabase`, and the bridge warning
- `GRANT dollas_app TO current_user` at the end of `APP_GRANT_SQL`
- `APP_ROLE_SQL` (the NOLOGIN fallback create)

After that, make `DATABASE_URL_APP` required on Vercel.

```bash
export PULUMI_BACKEND_URL=file://$(mktemp -d) PULUMI_CONFIG_PASSPHRASE=throwaway
pulumi stack init scratch
pulumi config set --secret dollas:ownerDatabaseUrl postgresql://owner:pw@127.0.0.1:5433/neondb
pulumi config set dollas:vercelProjectId prj_fake
pulumi config set --secret vercel:apiToken 0123456789abcdef01234567
pulumi preview --diff
```

`pulumi up --target` on the password and `dollas-app-login` URNs then runs the SQL for real against that database. The Vercel resource needs a real token.
